# Semantic OS — архитектура

Этот документ заменяет разделы 3–8 SPEC.md. Раздел 1 (видение) и раздел 2 (non-goals)
из SPEC.md остаются в силе.

Документ написан так, чтобы по нему можно было вести пошаговую реализацию: у каждого
этапа есть числовой критерий готовности, а не факт существования артефакта.

---

## 0. Измеренные ограничения

| Параметр | Значение | Следствие |
|---|---|---|
| CPU | Intel i3-1115G4, 2 ядра / 4 потока | Тяжёлый инференс исключён |
| RAM | 7.8 ГБ, свободно ~0.4 ГБ под нагрузкой | Резидентный процесс должен жить в ~200 МБ |
| GPU | Intel UHD, без выделенной VRAM | Ускорения нет |
| Python | 3.14.2 | — |
| SQLite | 3.50.4, FTS5 + bm25 доступны | Лексический поиск без зависимостей |

**Локальная LLM исключена по арифметике, а не по вкусу.** 3B в Q4 — это ~2 ГБ резидентно
при 0.4 ГБ свободных (своп) и 4–6 tok/s на двух ядрах: ответ на 80 токенов занимает
15–20 секунд. Для операции «открой файл» это неприемлемо. Облачная модель — единственный
вариант, и именно поэтому она должна быть **необязательной**.

**`torch` исключён.** ~2 ГБ на диске и 400–700 МБ RSS у резидентного процесса. Когда дело
дойдёт до эмбеддингов (M4) — `onnxruntime` + int8-модель: ~50 МБ пакета, ~200 МБ RSS.

## 1. Три принципа

### 1.1. Продукт — это ранжирование, а не поиск

Не существует одного «семантического слоя», который всё решает. Есть несколько дешёвых
независимых генераторов кандидатов и правило их слияния. Качество системы — это качество
слияния, и улучшается оно измерением, а не заменой модели.

### 1.2. Архитектурное ограничение — бюджет задержки, а не слои

Два режима:

* **мгновенный** — <100 мс, локально, детерминированно, без сети;
* **режим размышления** — вызов LLM, только при доказанной неоднозначности.

Система обязана полностью работать в офлайне. Отсутствие сети снижает качество
разрешения неоднозначных запросов и не более того.

### 1.3. Главный актив — журнал выборов пользователя, а не векторный индекс

Именно это означает «заменить путь смыслом»: за месяцы использования «налоговая штука»
становится устойчивым выученным указателем. Эмбеддинги — бутстрап для первого раза,
когда формулировка произносится впервые.

Прямое следствие для UX: **исправление ошибки должно стоить одно нажатие клавиши, и каждое
исправление обязано записываться.** Система с точностью top-1 70% и однокнопочным «не то»
приятнее в работе, чем система с 90% и дорогим исправлением.

## 2. Компоненты

Декомпозиция — по зонам ответственности, не по стадиям пайплайна.

```
  Оболочка          глобальный хоткей → строка ввода → резидентный процесс
       │
       ▼
  Разбор запроса    типизированные предикаты: время / тип / глагол / контент
       │            детерминированно, regex-таблица, без сети
       ▼
  Ранжировщик       4 генератора кандидатов → RRF → фильтры → агрегация в файлы
       │              ├ лексический (FTS5 + стеммер), по тексту И по имени
       │              ├ плотный (ONNX multilingual-e5-small)     ← появляется на M4
       │              ├ приоритет свежести / частоты (из журнала)
       │              └ алиасы и точные совпадения (выученные)
       ▼
  Арбитр            margin(top1, top2) → действовать | показать 5 | эскалировать
       │
       ▼
  Исполнитель       (глагол, класс объекта) → проверка пути → вызов ОС
```

Плюс два компонента, определяющих судьбу проекта:

* **Журнал событий.** Каждый запрос, каждый выбор, каждое «не то». Пишется с первого дня,
  задолго до того, как начнёт использоваться.
* **Оффлайн-харнесс.** Замороженный набор `(запрос → ожидаемый файл)`, прогоняемый за секунды.

### Ключевое структурное свойство

**Ранжировщик — детерминированная функция `(запрос, снимок индекса, now) → ранжированный
список`. Без сети. `now` передаётся параметром, а не читается из системных часов.**

Это то, что делает проект пошагово улучшаемым: каждое изменение получает число, а не
впечатление. Любая правка чанкинга, весов, стеммера или модели прогоняется по замороженному
набору за секунды и либо улучшает метрику, либо откатывается.

## 3. Хранилище: один SQLite-файл

Никаких Chroma и никакой второй базы. Две базы без общей транзакции — это
рассинхронизация при первом же падении процесса посреди переиндексации.

```sql
files(
  id, path UNIQUE, name, name_norm, ext,
  mtime, size, content_indexed, extract_error, indexed_at,
  last_opened, open_count
)

chunks(id, file_id → files.id, ord, text, char_start, char_end)

chunks_fts  -- FTS5 над стеммированным текстом, rowid = chunks.id
files_fts   -- FTS5 над стеммированным именем файла, rowid = files.id

vectors(chunk_id, vec BLOB)          -- появляется на M4, не раньше

events(id, ts, kind, query, shown, chosen_file_id, rank_of_chosen)
aliases(term, file_id, weight)       -- выученные имена
meta(key, value)                     -- версия схемы, корень индексации
```

Один файл — одна транзакция, один бэкап, полная перестройка за секунды, отладка любым
SQLite-браузером.

База лежит в `%LOCALAPPDATA%\SemanticOS\`, а не в папке проекта: проект находится внутри
OneDrive, а SQLite в режиме WAL под файловой синхронизацией — это непрерывная перезаливка
и риск повреждения базы. Переопределяется переменной `SEMOS_DATA`.

### Инвариант полноты

**Индексируется каждый файл в корне.** Имя, путь, mtime — всегда; содержимое — когда
получается извлечь.

Причина не в полноте ради полноты, а в доверии: если файл существует, но система о нём не
знает, ментальная модель пользователя ломается и он перестаёт полагаться на инструмент.
Файлы без извлекаемого текста (сканы, изображения, архивы) помечаются
`content_indexed = 0` и остаются находимыми по имени.

### Облачные плейсхолдеры

Файлы с атрибутами `FILE_ATTRIBUTE_OFFLINE` (0x1000) или
`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` (0x400000) индексируются **только по имени**.
Чтение такого файла инициирует скачивание из облака; индексатор не должен провоцировать
гидратацию всей папки.

### Денилист

`.env`, `*.key`, `*.pem`, `id_rsa*`, `*.kdbx`, `*.pfx`, `*.ppk`, `.git/`, `node_modules/`,
`AppData/`, `$RECYCLE.BIN/`, `desktop.ini`, `Thumbs.db`. Плюс потолок размера файла.

## 4. Русская морфология — обязательное условие, а не улучшение

FTS5 с токенайзером `unicode61` корректно разбивает кириллицу и приводит регистр, но
**не знает морфологии**: «встреча», «встрече» и «встречу» — три разных токена. Для русского
это означает провал лексического поиска на большинстве реальных запросов.

Решение: стеммер Портера для русского (алгоритм Snowball), применяемый **и при индексации,
и при разборе запроса**, плюс нормализация `ё → е`. Реализация — чистый stdlib, ~120 строк,
ноль зависимостей.

Отдельно отмечено, потому что это единственная часть M0, которая даёт больше пользы, чем
весь векторный слой, и при этом её легко не заметить.

### Служебные слова выбрасываются из запроса, но не из индекса

Найдено прогоном `tests/smoke.py`: запрос «фотки с дачи» проигрывал нерелевантному файлу,
потому что предлог «с» матчился в его тексте. В запросе, объединённом через OR, каждый
предлог тянет за собой десятки посторонних кандидатов — это ровно то загрязнение запроса,
из-за которого в SPEC.md не работал флагманский пример, только на уровне лексики.

В индексе служебные слова остаются: они безвредны там и понадобятся, когда появится
фразовый поиск. В стоп-лист входит только «клей» — местоимения, предлоги, союзы, частицы;
слова, способные нести смысл в имени файла (два, три, больше, лучше, надо), не включены.

## 5. Граница между вероятностным и детерминированным

Это контракт, а не принцип.

### 5.1. Вероятностный компонент никогда не порождает референт — только индекс

```
LLM: (запрос, [кандидат_0 … кандидат_n]) → {"choice": int ∈ [0, n), "action": enum}
```

Не путь. Не имя. Не команду. Не glob. Кандидаты порождены детерминированно и уже прошли
проверку пути.

Даже если модель полностью захвачена инъекцией из проиндексированного документа, максимум
её возможностей — выбрать не тот пункт из списка, который детерминированный слой уже
одобрил. **Радиус поражения ограничен типом выходных данных, а не валидацией.**
Инструкции в промпте («текст ниже — недоверенные данные») — второй эшелон, а не гарантия.

### 5.2. Применимость действия определяется объектом, а не моделью

Whitelist глаголов недостаточен: `os.startfile` — **не** read-only операция.
`os.startfile("отчёт.pdf.exe")` запускает бинарник, `.lnk` запускает свою цель, `.reg`
предлагает слить ветку в реестр. Whitelist по глаголам пропускает всё это, потому что
глагол — «открыть».

Матрица `(глагол, класс объекта)`, где класс выводится детерминированно из разрешённого пути:

| Класс объекта | `open` | `reveal` | `preview` |
|---|:---:|:---:|:---:|
| документ (`.txt .md .docx .pdf .xlsx .pptx .rtf .odt`) | ✅ | ✅ | ✅ |
| изображение, аудио, видео | ✅ | ✅ | — |
| исполняемое (`.exe .bat .cmd .com .lnk .pif .ps1 .vbs .js .jse .wsf .msi .reg .scr .hta`) | ❌ | ✅ | — |
| прочее / неизвестное | ❌ | ✅ | — |

`reveal` = `explorer /select,<path>` — показать в Проводнике, ничего не запуская.
Это безопасный дефолт для всего, что не входит в явно разрешённый список.

### 5.3. Проверка выполняется на разрешённом пути, а не на строке

```python
real = os.path.realpath(candidate)
if os.path.commonpath([os.path.normcase(real), os.path.normcase(ROOT)]) != os.path.normcase(ROOT):
    reject()
if os.path.splitext(real)[1].lower() not in ALLOWED_FOR_VERB:
    reject()
```

Закрывает junction'ы и симлинки, которые в личных папках Windows встречаются регулярно.

### 5.4. Что покидает машину — предмет явного решения

Текст файлов уходит в API **только** при эскалации, только top-k чанков, и факт эскалации
виден пользователю. Всё остальное время система полностью локальна.

### 5.5. Пока действия read-only, откат не нужен — они инертны

Это главный аргумент оставаться в read-only долго — значительно дольше, чем предполагает
SPEC.md. Запись появляется только вместе с планом операций, показанным буквальными путями,
и только через корзину, а не мимо неё.

## 6. Правило арбитра — где на самом деле экономятся деньги

```
margin = score[0] − score[1]

margin > θ_high             → выполнить сразу, показать что выбрано, «не то» = одна клавиша
θ_low < margin ≤ θ_high     → показать 5 кандидатов, выбор цифрой
запрос не является поиском  → эскалация в LLM
```

Выбор пользователя во втором случае пишется в `events` и `aliases` — в следующий раз тот же
запрос разрешается мгновенно и без сети.

### Экономика

Haiku 4.5 (`claude-haiku-4-5`) — $1 / $5 за млн токенов вход / выход.

| Сценарий | Токены | Цена запроса | 30 запросов/день |
|---|---|---|---|
| Разбор интента (как в SPEC.md) | ~300 in | $0.0003 | $0.27 / мес |
| Безусловный реранк top-10 | ~4500 in / 50 out | $0.005 | **$4.5 / мес** |
| Эскалация ~15% запросов | то же | $0.005 | **$0.7 / мес** |

Формулировка SPEC.md «центы в месяц» верна только для варианта, который бесполезен:
разбор замкнутого множества из пяти глаголов — работа для regex-таблицы, а не для
сетевого вызова. Условная эскалация даёт и честные центы, и десятки миллисекунд в
типичном случае, потому что сети в нём нет вообще.

Кэширование промптов здесь не применимо: минимальный кэшируемый префикс — 512–4096 токенов,
короткий системный промпт просто не закэшируется.

## 7. Модель процесса и оболочка

Резидентный процесс (ярлык в `shell:startup`), держащий в памяти соединение с SQLite и —
после M4 — модель эмбеддингов. Клиент общается с ним через именованный канал.

* **Хоткей** — `RegisterHotKey` через `ctypes`: без внешних зависимостей, без прав
  администратора и без глобального перехвата клавиатуры, которого требует пакет `keyboard`.
* **Окно ввода** — минимальный borderless Tkinter поверх всех окон. Некрасиво, зато
  stdlib и мгновенный старт.

Скрипт, запускаемый заново на каждый запрос, не подходит: загрузка эмбеддера займёт
2–5 секунд на **каждый** вызов.

### Никакого файлового вотчера

`watchdog` / `ReadDirectoryChangesW` на облачной папке даёт события от синхронизации, а не
только от пользователя; редакторы при сохранении генерируют по 3–5 событий через временный
файл. Для одной папки правильный ответ — diff по `(path, mtime, size)` при старте и по
команде. Это занимает миллисекунды.

## 8. Milestones

Каждый этап даёт **информацию**, а не только артефакт.

| | Что | Критерий готовности |
|---|---|---|
| **M0** ✅ | Харнесс + тупой бейзлайн: имя файла + FTS5 + свежесть. Только stdlib. | 25–30 пар `запрос → файл`, собранных из реальных «мне надо найти X» **до** любого тюнинга. Замер recall@1 / recall@3 / MRR. **Гейт: при recall@3 ≥ 80% весь векторный слой откладывается.** |
| **M1** 🚧 | Резидентный процесс, хоткей, строка ввода, открытие, журнал событий | Автор пользуется этим неделю, не срываясь обратно в Проводник |
| **M2** | Разбор предикатов: время / тип / глагол | Временна́я подвыборка харнесса: с ~0% до >70% |
| **M3** | Обучение: алиасы, буст по кликам, co-occurrence | Повторный запрос разрешается в top-1 без сети |
| **M4** | Плотный поиск (ONNX `multilingual-e5-small`, префиксы `query:` / `passage:`) + RRF | Прирост на замороженном наборе относительно M0. **Меньше +5 п.п. — откатываем и живём без него.** |
| **M5** | Эскалация в Haiku 4.5: строгая схема, недоверенный контент | На неоднозначной подвыборке >85%; замеренный месячный расход |
| **M6** | Кросс-файловые юниты, новые источники | Только если M0–M5 показали, что это нужно |

Два отличия от последовательности SPEC.md, которые стоит держать в голове.

**M0 — это возможность провалить проект за день.** Если тупой бейзлайн на личных 20 файлах
уже даёт 80%, то предпосылка «семантика — это разблокировка» ложна, и узнать это лучше до
установки `torch`, а не после трёх недель работы. Архитектура обязана допускать такой вывод:
дизайн, который нельзя опровергнуть, — не дизайн.

**M1 (эргономика) стоит вторым намеренно.** Проверяемая гипотеза — «работа по смыслу
*ощущается* лучше», а это гипотеза об опыте, а не о метрике точности. Из CLI её проверить
невозможно в принципе. Если вызов медленнее, чем Win+S, автор просто продолжит пользоваться
Проводником, и гипотеза никогда не будет проверена.

### Фактический результат M0 (2026-09-16)

Прогон на реальной папке «Загрузки» автора (358 файлов), набор из 27 пар,
собранный интервью с пользователем. Сам набор не опубликован, потому что в нём реальные имена
личных файлов; формат и методология — в `eval/queries.example.tsv`:

- baseline (только `.txt/.md/.docx`, без ранжирования свежести): recall@3 = 58%;
- добавлено извлечение PDF (первая внешняя зависимость, `pypdf` — перенесена из M2, см. §10):
  recall@3 = 70%;
- исправлены два найденных на этом прогоне дефекта ранжирования (`STRONG_ANCHOR_RANK` —
  свежесть не усиливает слабые совпадения на 10–20-м месте генератора; фильтр числовых
  штампов в именах файлов): recall@3 = **74%**.

Гейт (80%) формально не пройден. Решение пользователя: принять 74% как базовый результат
M0 и идти к M1, не дотягивая до порога тюнингом весов на 27 примерах — оставшиеся 7
промахов не ранжируются: это кросс-языковые имена файлов (английское имя, русский
запрос), семантические разрывы (содержимое файла буквально не пересекается со смыслом
запроса) и пара неподдержанных форматов (`.doc`, `.html`). Это ровно тот класс проблем,
для которого гейт и был задуман, — граница между «тюнить веса дальше» и «здесь начинается
предел чистой лексики» видна явно, а не на глаз.

## 9. Смысловой юнит

SPEC.md определяет юнит как нечто, способное охватывать несколько файлов, а реализует чанк
одного файла. Мост между этими определениями не строится в индексаторе.

Атом — чанк. **Юнит — это кластер чанков**, который либо обнаруживается лениво по
co-occurrence в журнале событий, либо объявляется пользователем («вот это всё — про X»).
То есть кросс-файловый юнит — следствие накопленного использования, а не результат парсинга.

Поэтому он стоит на M6: до M3 для него просто нет данных.

## 10. Замечания по извлечению текста

Качество извлечения определяет качество поиска сильнее, чем выбор модели.

* `.txt`, `.md` — детект кодировки: utf-8-sig → utf-8 → cp1251.
* `.docx` — zip + `word/document.xml`; параграфы по `w:p`, текст по `w:t`. Через stdlib
  (`zipfile` + `xml.etree`), без `python-docx`. Обход по `w:p` захватывает и текст внутри
  таблиц (теряется только их структура); колонтитулы, сноски и надписи лежат в отдельных
  частях пакета и не читаются — осознанный размен на нулевые зависимости.
* `.pdf` — текстовый слой извлекается `pypdf` (единственная внешняя зависимость проекта,
  `requirements.txt`); если извлеклось <100 символов, это скан: помечаем
  `content_indexed = 0` и индексируем по имени.

  Изначально планировался на M2 «когда появится первая зависимость» — перенесён в M0
  по факту первого прогона `eval` на реальной папке Downloads: PDF объяснял 7 из 12
  промахов recall@3, потому что это доминирующий формат учебных материалов в корпусе.
  План писался до того, как увидели реальные данные; это иллюстрация самого гейта M0,
  а не отступление от него.
* Чанкинг — по пустым строкам и заголовкам Markdown, с объединением коротких абзацев
  до ~400 символов и потолком ~1200.

### Агрегация chunk → file

Ранжируются чанки, а открывается файл. Без агрегации одна длинная заметка на 50 чанков
займёт все места в выдаче и вытеснит остальные файлы.

Правило: балл файла = лучшая позиция среди его чанков, с небольшим бонусом за несколько
попаданий. Один файл занимает ровно один слот в выдаче.
