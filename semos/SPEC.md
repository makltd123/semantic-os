# Semantic OS — надстройка над файловой системой, работающая по смыслу, а не по путям

## 1. Видение

Обычная ОС адресует данные через точные идентификаторы: путь к файлу, точное имя. Пользователь обязан помнить, где и как что-то называется.

Semantic OS — это **надстройка поверх обычной ОС** (не замена ядра, не новая ФС на диске), которая меняет единицу, с которой работает пользователь: вместо "файл по пути" — "смысловой юнит" (meaning unit). Юнит — это осмысленный кусок информации (заметка, тема переписки, идея, документ), который может состоять из частей нескольких файлов или быть частью одного файла среди прочих тем.

Система должна уметь: по запросу вида "открой ту штуку про встречу на прошлой неделе" находить и открывать нужный реальный файл, даже если пользователь не помнит ни имени, ни расположения.

## 2. Non-goals (что мы сознательно НЕ делаем в этой версии)

- Не пишем ядро, драйверы, загрузчик — работаем в userspace поверх Windows.
- Не делаем мультипользовательскую систему.
- Не делаем кросс-платформенность — целевая платформа: **Windows**.
- Не индексируем весь диск сразу — только одну выделенную тестовую директорию.
- Не выполняем деструктивные операции (удаление, перезапись) без явного отдельного подтверждения — см. раздел 6 (Safety).
- Не оптимизируем производительность — цель этой стадии: проверить саму гипотезу, что поиск/работа "по смыслу" вообще ощущаются лучше, чем по путям.

## 3. Архитектура: 4 слоя

```
Пользователь (естественный язык)
        │
        ▼
[4] Исполнитель действий  ──► реальные вызовы к Windows (открыть файл, показать список)
        ▲
        │ структурированное действие
        │
[3] Резолвер запросов  ──► LLM через API (по одному вызову на запрос пользователя)
        ▲
        │ ищет по
        │
[2] Хранилище смыслов  ──► векторная БД + метаданные/связи
        ▲
        │ наполняется
        │
[1] Индексатор  ──► следит за тестовой папкой, режет файлы на юниты, считает эмбеддинги локально
        ▲
        │
   Реальные файлы в тестовой папке
```

### Слой 1 — Индексатор
- Следит за выделенной тестовой папкой (см. раздел 5).
- На старте: разово сканирует все файлы, разбивает содержимое на смысловые куски (чанки — по абзацам/секциям, не по фиксированному числу символов, если это оправдано типом файла).
- Для каждого чанка считает эмбеддинг **локально**, без API.
- Сохраняет: текст чанка, эмбеддинг, путь к исходному файлу, позицию в файле, время изменения.
- В дальнейшем (M4): фоновый watcher на изменения файлов в папке, реиндексация только изменённого.

### Слой 2 — Хранилище смыслов
- Векторная БД для эмбеддингов + поиска по близости.
- Отдельно — структурированные метаданные и связи между юнитами (какой юнит из какого файла, к какому "проекту/теме" условно относится — на первой версии связи могут быть минимальными).
- Всё локально, никакого внешнего хранения данных пользователя.

### Слой 3 — Резолвер запросов
- Принимает фразу на естественном языке от пользователя.
- Один вызов к LLM через API, возвращающий структурированный intent по фиксированной JSON-схеме: `{action, query_description, target_hint}`.
- `query_description` используется для векторного поиска в Слое 2, результат — ранжированный список кандидатов (юнит + исходный файл + оценка релевantности).
- LLM здесь не исполняет действия — только переводит фразу в структуру и в поисковый запрос.

### Слой 4 — Исполнитель действий
- Получает структурированное действие + выбранный юнит/файл.
- Проверяет действие против явного списка разрешённых операций (whitelist) — см. раздел 6.
- Только после проверки выполняет реальный вызов ОС (открыть файл в связанной программе, показать содержимое и т.д.).

## 4. Технологический стек

| Компонент | Выбор | Почему |
|---|---|---|
| Язык | Python 3.11+ | Быстрая итерация, богатые библиотеки под embeddings/LLM, скорость выполнения не критична на этой стадии |
| Локальные эмбеддинги | `sentence-transformers`, модель `all-MiniLM-L6-v2` | ~80 МБ, работает на CPU без видеокарты, секунды на пакет файлов |
| Векторное хранилище | `chromadb` (локальный, файловый режим) | Не требует отдельного сервера, тривиально поднимается на Windows |
| Метаданные/связи | SQLite (`sqlite3`, встроен в Python) | Простая структура для путей, времени изменения, связей юнитов |
| LLM для резолвинга намерения | Claude API, модель Haiku | Дешёвая модель, вызывается один раз на пользовательский запрос, не на файл |
| Слежение за файлами | `watchdog` | Кроссплатформенная библиотека, поддерживает Windows |
| Открытие файлов в Windows | `os.startfile()` | Штатный способ открыть файл ассоциированной программой в Windows |

## 5. Стартовый scope (M0)

- Тестовая папка: `%USERPROFILE%\SemanticOS\test-notes` (создать вручную, положить туда 10–20 реальных файлов: заметки, документы — то, чем пользователь реально пользуется, не синтетика).
- Поддерживаемые типы файлов в v1: `.txt`, `.md`, `.docx`. PDF и изображения — не в этой версии.
- Никакой обработки системных/бинарных файлов.

## 6. Правила безопасности (Capability layer)

Резолвинг вероятностный (LLM может ошибиться в интерпретации) — исполнение должно быть детерминированным и ограниченным:

- Явный whitelist разрешённых действий в Слое 4. На M0–M2: **только чтение** (найти, показать путь, открыть в программе по умолчанию). Никаких `delete`, `overwrite`, `move` до отдельного явного этапа с подтверждением на каждое действие.
- Любое действие, помеченное как потенциально необратимое, требует явного подтверждения пользователя в моменте — независимо от того, насколько уверенно резолвер интерпретировал запрос.
- Резолвер (Слой 3) никогда не вызывает Слой 4 напрямую в обход whitelist-проверки.

## 7. Milestones

- **M0 — Индексатор.** Сканирование тестовой папки → чанки → локальные эмбеддинги → сохранение в Chroma + SQLite. Критерий готовности: скрипт проходит по папке и создаёт непустую БД юнитов.
- **M1 — Семантический поиск (CLI).** Ввод фразы → векторный поиск по Слою 2 → топ-3 релевантных файла с путями. Без LLM-резолвера — просто прямой embedding запроса и поиск по близости. Критерий готовности: на 5 тестовых запросах правильный файл оказывается в топ-3 минимум в 4 случаях.
- **M2 — Резолвер намерений.** Подключение LLM через API: свободная фраза → структурированный intent → уточнённый поисковый запрос → результат. Критерий готовности: система корректно определяет `action` (например "открой" vs "покажи список") на 10 разных фразах.
- **M3 — Исполнитель действий + capability layer.** Реальное открытие файлов через `os.startfile()`, whitelist только на чтение.
- **M4 (стретч) — Фоновый watcher.** Автоматическая реиндексация изменённых файлов без ручного перезапуска.

## 8. Модель стоимости (для явности)

- Индексация: 0 обращений к API — всё локально.
- Один пользовательский запрос = 1 обращение к Haiku. При личном использовании (десятки запросов в день) — стоимость на уровне центов в месяц.

## 9. Будущие направления (не в этой спеке, но держим в уме)

- Голосовой ассистент ("свой джарвис") — надстройка над Слоями 3–4: голосовой ввод/вывод + постоянная сессия с контекстом диалога. Не требует пересмотра архитектуры, использует те же слои.
- Расширение источников для индексации: буфер обмена, история браузера, другие папки.
- Кэширование частых резолвов, чтобы не ходить в API повторно на похожие запросы.
